# セキュリティ修正の反映前確認

出金・失敗した wrap の返金は、対象金額から ledger 手数料を差し引いて送金する。例えば burn 額が 1000、手数料が 100 の場合、受取額は 900。送金額と手数料の合計が backing を超えないよう、手数料を明示して送金する。

新しい出金・返金は、手数料と `created_at_time` を送金前に保存する。応答が不明な場合は同じ内容で再試行する。初回の送金試行が `BadFee` で拒否された場合だけ、新しい手数料を取得できる。過去の送金結果が不明な再試行では、`BadFee` を受けても取引情報を保持する。手数料変更で同じ取引を再送できない場合は、ledger の履歴と照合して解決する。古い処理の応答で、完了済みの要求や別の再試行を上書きしない。

## アップグレード前

- 旧版で送金を試みた未完了の出金・返金を、可能な限り旧版の間に解決する。
- 応答が不明な要求は ledger の履歴と照合する。既に成立している送金を、新しい金額で再送しない。
- 旧版が保持した未払い要求には、確定した支払い拒否と結果不明の履歴を区別する情報がない。新版でも一括削除せず、支払い結果を照合する。既に占有された受付枠は、この修正だけでは回収されない。
- 旧版の要求には送金時刻だけが保存され、手数料が保存されていない場合がある。この場合、新版は `legacy_transfer_requires_reconciliation` で自動再送を停止する。送金結果を確定できていない要求が残る場合はアップグレードを保留する。
- 今回の作業では本番へのデプロイ・送金・状態変更を実行していない。

## リソース上限

未払い・支払結果が不明な wrap と native deposit は、既存の admission 上限を共有し、全体 8192 件、principal ごとに 32 件まで保持する。初回の手数料徴収で ledger が支払いを拒否した場合は、要求と受付枠を削除し、再送を新規要求として扱う。応答が不明な場合は要求を保持し、再試行は同じ要求 ID を使う。その後の拒否応答だけでは過去の支払い成功を否定できないため、枠を解放しない。支払いが確認されれば枠を解放する。

wrap の mint receipt は 1 回に 256 件まで走査し、必要な間だけ timer で続行する。走査中に block が生成された場合は、現在の走査を完了した後で再走査する。

## 検証

リポジトリ標準の `cargo check --workspace`、関連 crate のテスト、TypeScript のテストと型チェックを実行する。出金・返金・upgrade の実動作は `wrap_unwrap_flow_e2e` で公式 ICRC ledger と PocketIC 12 を使って確認する。

標準 CI は `forge` が必要。PocketIC は実行ホストの CPU に対応したバイナリを指定する。ローカルテストの通過だけで本番反映の承認としない。
